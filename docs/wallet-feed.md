# Finalized wallet feed

`scripts/export-wallet-feed.mjs` is an independent, read-only exporter for the website's `robinhook.wallet-feed.v1` format. It does not load a wallet, read signing secrets, sign, submit transactions, change payouts or activate the website's token identity. Production deployment verification uses the configured operator address without a signer.

After the real ROBIN launch is finalized and `config.production.json` has verified deployment addresses and runtime hashes:

```text
node scripts/export-wallet-feed.mjs config.production.json --once
node scripts/export-wallet-feed.mjs config.production.json --loop
```

Set `ROBIN_RPC_URL` (or the configured RPC environment variable) to the archive-capable HTTPS RPC. Set `ROBIN_WALLET_FEED_STATE_DIRECTORY` to a dedicated durable directory, separate from `ROBIN_STATE_DIRECTORY`. The default is `output/wallet-feed`. Only `recovery-snapshot.json` is public output; never serve the raw snapshot cache, payment cache, operator journal, RPC configuration or secrets.

The exporter has its own lock and configuration-bound caches. The first run replays the canonical v4 token ledger and scans the distributor's complete reward history from the configured token deployment block. Later cycles validate the saved payment schema, configuration, campaign baseline, numeric reconciliation and canonical finalized checkpoint, then scan only subsequent blocks. Every cycle reads the finalized pending balance for recipients touched by new reward events and for every previously unpaid recipient, plus the total reserved balance. Other pending values follow from cumulative verified allocations minus payments: the pinned distributor changes pending only through those events. New ledger holders without allocation history have proven zero payments and need no mapping read. A restart preserves previous paid totals. Corrupt, mismatched, backward or forked caches fail closed instead of silently resetting. A cold start still requires full archive history; measure RPC usage with the intended holder count before activation.

The loop refreshes every 300 seconds by default. `ROBIN_WALLET_FEED_INTERVAL_SECONDS` may set 60–600 seconds. Old caches remain private when a cycle fails, while the public output becomes `unavailable` with no account values. Feed generation must be less than 15 minutes old; its finalized checkpoint must be less than 30 minutes old. These limits are separate because normal chain finality can already be around 17 minutes behind the latest head. Refreshing a feed never extends its checkpoint deadline or changes its finalized accounting time.

The delivery boundary is 2 MiB of UTF-8 JSON, enforced both before local ready output and before upload. Larger snapshots fail closed; accounts are never silently omitted. No production holder capacity is admitted yet. The local 1,000-account test produces 423,455 JSON bytes; 5,000 similarly shaped accounts exceed the cap, and exact capacity varies with record values. Sharded delivery is not implemented. Incremental pending RPC work scales with changed reward recipients and unpaid recipients rather than all token holders. A quiet 1,000-account mock with no allocations uses zero `pending(address)` calls; 1,000 persistently unpaid recipients still require 288,000 calls per day at five-minute refresh. Chain verification, archive logs/state and reserved-balance work remain additional costs. The local mock records call count, JSON size and CPU time; it does not measure live RPC latency, archive-provider quotas or hosting memory. Those measurements at the intended holder count remain a launch gate, not an unlimited-scale claim.

Payment evidence requires successful canonical receipts and finalized historical calls. Actual `RewardPaid` events supply received ETH; cumulative allocations minus payments supply allocated but unpaid ETH, verified by `pending(address)` for changed or previously unpaid recipients. Repeated `RewardDeferred` events are not summed. Derived pending values must match every checked mapping, and their sum must equal the distributor's reserved balance. Token-inventory relief is a separate value that moves with tokens and is not a wallet's payment history. Tiers use exact remaining-loss/basis ratios, with equal ratios sharing a tier; percentages are rounded only for display.

Campaign separation is mandatory. The distributor must have no reserved rewards immediately before the token deployment block, or must not yet exist at that historical block. Every subsequent allocation must come from a direct `distributeEligible` call bound to the configured token. Legacy allocation methods, allocation through another transaction target, another token's allocation and uncleared prior pending funds stop export. This is a conservative attribution boundary, not a claim that event logs identify tokens. RPC log completeness remains a trusted-provider assumption; receipt matching and balance reconciliation detect inconsistent evidence.

Optional delivery uses both `ROBIN_WALLET_FEED_URL=https://robinhook.wtf/api/wallet-snapshot` and `ROBIN_WALLET_FEED_PUBLISH_TOKEN`, supplied securely by the host. The token must contain at least 32 characters without whitespace. The URL must be HTTPS with the exact `/api/wallet-snapshot` path, no embedded credentials, query or fragment. The exporter sends public JSON using `PUT`, bearer authentication, no redirects and a maximum 10-second timeout. The endpoint must return HTTP 200 with a JSON acknowledgement containing `status: "stored"` or `"unchanged"` and the submitted `generatedAt`. A stored acknowledgement must also echo the checkpoint (or null for unavailable). Failure details never print URLs, credentials or response bodies. The endpoint, authentication, storage and browser delivery must be separately deployed and verified before enabling this option; this repository does not provision them.

After verifying real end-to-end export and delivery, pin the website's exact chain/token/distributor identity. Until then, leave its live identity unset and its public feed inactive. Local tests are not evidence of an actual token launch, live payouts or successful hosting.
